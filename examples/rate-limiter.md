# Проектирование Rate Limiter

**Задача:** ограничить число запросов от клиента за интервал. Общий компонент, который стоит перед API.

---

## 1. Требования

### Функциональные
- Ограничение по разным ключам: user_id, IP, API-ключ, эндпоинт
- Разные лимиты на разные эндпоинты (100 req/мин на чтение, 10 req/мин на запись)
- Ответ `429 Too Many Requests` с заголовками `X-RateLimit-*` и `Retry-After`
- Возможность белого списка (внутренние сервисы)

**За рамками:** биллинг по квотам, динамические лимиты от ML.

### Нефункциональные
- **Масштаб:** 1 млн RPS суммарно на кластер
- **Latency:** решение < 1 мс (P99) — стоит на пути каждого запроса
- **Точность:** допустима небольшая пере- или недо-блокировка (не критично, если клиент изредка получит 429 на 1 запрос раньше)
- **Доступность:** при отказе лимитера — **fail-open** (пропускаем запросы), а не fail-closed. Лечь целиком из-за лимитера хуже, чем пропустить лишний трафик.
- **Распределённость:** лимит общий для всех инстансов API (не 100 × N инстансов)

---

## 2. Алгоритмы

### 2.1 Fixed Window (фиксированное окно)
Счётчик на окно (например, минута): `INCR key`, если > limit → 429.

- ✓ Просто, один `INCR`
- ✗ **Проблема границы:** лимит 100/мин. Клиент отправляет 100 в 12:00:59 и 100 в 12:01:00 → 200 за 2 секунды. Двойной всплеск.

### 2.2 Sliding Window Log
Храним timestamp каждого запроса, считаем те, что попадают в последние N сек.

- ✓ Точный, нет проблемы границы
- ✗ **Память:** 100 запросов × 16 байт на пользователя × 1 млн пользователей = 1.6 ГБ и растёт с лимитом. Для лимита 10k/час — неприемлемо.

### 2.3 Sliding Window Counter
Комбинация: счётчики по минутам + взвешивание.

```
rate = prev_window_count × (1 - elapsed/window) + current_window_count
```
Окно 60 сек, прошло 15 сек → вес прошлого окна 0.75.

- ✓ Мало памяти (2 счётчика на ключ)
- ✓ Сглаживает границу
- ✗ Приблизительно (ошибка до нескольких процентов)

### 2.4 Token Bucket
Ведро ёмкостью `B`, пополняется со скоростью `r` токенов/сек. Запрос стоит 1 токен.

- ✓ **Разрешает burst** до B (полезно: клиент может отправить пачку)
- ✓ Средняя скорость строго `r`
- ✓ Два параметра: `B` (burst) и `r` (устойчивая скорость) — гибкая настройка
- ✗ Нужны `last_refill_ts` и `tokens` на ключ (два значения)

### 2.5 Leaky Bucket
Очередь фиксированного размера, «протекает» с постоянной скоростью.

- ✓ Строго равномерный выход, нет burst
- ✗ **Не подходит для API**: клиент, отправивший пачку легальных запросов, получает задержку, а не быстрый ответ

### 2.6 Сравнение

| Алгоритм | Память/ключ | Точность | Burst | Сложность |
|---|---|---|---|---|
| Fixed Window | 1 счётчик | низкая (границы) | да, двойной | тривиальная |
| Sliding Log | O(limit) | точная | нет | средняя |
| Sliding Counter | 2 счётчика | ~95% | ограниченный | средняя |
| **Token Bucket** | 2 числа | точная | **да, контролируемый** | низкая |
| Leaky Bucket | 1 очередь | точная | нет (задержка) | средняя |

**Выбор для API-гейтвея: Token Bucket.** Даёт контролируемый burst (важно для нормальных клиентов, которые шлют пачками) и строгую среднюю скорость.

## 3. Реализация Token Bucket

### Классика (хранить состояние)
```
tokens = min(B, tokens + (now - last_ts) × r)
last_ts = now
if tokens >= 1: tokens -= 1; allow
else: deny
```

### Проблемная сторона классики
Два числа на ключ → нужна транзакция (read-modify-write) → в Redis это `WATCH/MULTI` или Lua-скрипт.

### Решение: Lua-скрипт (атомарно на сервере)

```lua
-- KEYS[1] = ключ, ARGV = {capacity, refill_rate, now, cost}
local capacity = tonumber(ARGV[1])
local rate     = tonumber(ARGV[2])
local now      = tonumber(ARGV[3])
local cost     = tonumber(ARGV[4])

local data = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(data[1])
local ts     = tonumber(data[2])

if tokens == nil then
  tokens = capacity
  ts = now
end

tokens = math.min(capacity, tokens + (now - ts) * rate)

local allowed = 0
if tokens >= cost then
  tokens = tokens - cost
  allowed = 1
end

redis.call('HMSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('EXPIRE', KEYS[1], math.ceil(capacity / rate) + 60)
return {allowed, math.floor(tokens)}
```

Скрипт исполняется атомарно внутри Redis → нет гонок, один round-trip (~0.3 мс).

### Альтернатива: GCRA (Generic Cell Rate Algorithm)
Одно число вместо двух — «theoretical arrival time». Используется в nginx limit_req и в Cloudflare.
```
tat = max(tat, now) + 1/r
if tat - now > burst_window: deny
```
Меньше памяти и проще репликация, но сложнее объяснять. Для интервью — достаточно знать, что существует.

### Вариант в C#

```csharp
public sealed class TokenBucketLimiter
{
    private readonly IDatabase _redis;
    private readonly TimeProvider _time;

    public TokenBucketLimiter(IDatabase redis, TimeProvider time)
    {
        _redis = redis;
        _time = time;
    }

    public async Task<RateLimitResult> TryAcquireAsync(
        string key, int capacity, double refillPerSecond, int cost = 1)
    {
        var now = _time.GetUtcNow().ToUnixTimeMilliseconds() / 1000.0;

        var result = await _redis.ScriptEvaluateAsync(LuaScript,
            keys: [new RedisKey($"rl:{key}")],
            values:
            [
                capacity, refillPerSecond, now, cost
            ]);

        var values = (RedisResult[])result!;
        var allowed = (long)values[0] == 1;
        var remaining = (long)values[1];

        return new RateLimitResult(
            Allowed: allowed,
            Remaining: (int)remaining,
            RetryAfterSeconds: allowed
                ? 0
                : (int)Math.Ceiling(1.0 / refillPerSecond));
    }
}

public readonly record struct RateLimitResult(
    bool Allowed, int Remaining, int RetryAfterSeconds);
```

**Важно про `TimeProvider`:** время берётся на **клиенте** (API-инстансе), а не в Redis. Значит часы инстансов должны быть синхронизированы (NTP), иначе расход токенов будет скакать. Альтернатива — `redis.call('TIME')` внутри скрипта: точнее, но не работает в Redis Cluster (TIME на реплике может отставать).

## 4. Распределённая согласованность

### 4.1 Центральный Redis Cluster
Все инстансы API обращаются к общему Redis, ключ шардируется по `user_id`.

- ✓ Точный общий лимит
- ✗ Каждый запрос = +0.3–1 мс сетевого round-trip
- ✗ Redis — единая точка отказа (mitigated: fail-open + локальный fallback)

**Масштаб:** Redis Cluster из 10 нод держит ~1 млн ops/сек. Для 1 млн RPS на лимитер — на грани, нужен шардинг по ключу (что и делается автоматически).

### 4.2 Локальный лимитер + глобальный «кредит»
Инстанс имеет локальное ведро, пополняемое из Redis раз в N секунд.

- ✓ Нет round-trip на каждый запрос
- ✗ Возможен перерасход до N × burst
- Используется Cloudflare и крупными API

**Подход:** каждый инстанс получает квоту `limit / instance_count` и работает локально. Проблема — при несимметричном трафике инстансы бьют по разным квотам. Решение: периодический «обмен» остатками.

### 4.3 Гонки при «проверить и списать»
Классическая ошибка: `GET tokens` → `if ok: DECR tokens` — два запроса прочитали одно значение, оба списали → лимит превышен.

**Решение:** Lua-скрипт (атомарно), либо `DECR` с проверкой результата:
```
newValue = DECR key
if newValue < 0: INCR key; deny
```
Но это fixed-window, не token bucket.

## 5. Что отдавать клиенту

Заголовки (стандарт де-факто, IETF draft):
```
HTTP/1.1 429 Too Many Requests
Retry-After: 12
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1763400000
```

**Почему это важно:** клиент, который знает `Retry-After`, делает корректный backoff. Без него — ретраит немедленно и усугубляет.

**Разные лимиты на разные эндпоинты:** `429` должен содержать, какой лимит исчерпан (`X-RateLimit-Policy: read:100/m`), иначе клиент не понимает, что чинить.

## 6. Узкие места

### 6.1 Горячий ключ
Один клиент (или один IP за NAT — офис на 5000 человек) генерирует 30% трафика.
- Один ключ в Redis = один шард = перегрузка
- Решение: **локальный предфильтр**. Каждый инстанс держит in-process счётчик; если клиент явно превысил лимит, инстанс отклоняет локально, не доходя до Redis.
- Второй уровень: ключ разбивается на N субключей (`user:1:shard0..9`), запрос идёт в случайный, лимит делится на N. Точность падает в √N раз.

### 6.2 NAT и общие IP
Мобильный оператор: 100k пользователей за одним IP.
- Лимит по IP заблокирует всех
- Решение: лимит по IP — только как грубый анти-DDoS (например, 10k/мин), реальные лимиты — по user_id / API-ключу

### 6.3 Fail-open vs fail-closed
Redis недоступен. Что делать?
- **fail-open** (пропускаем): риск перегрузки бэкенда, но сервис живёт. Правильно для публичного API.
- **fail-closed** (блокируем): защита от перегрузки, но полный простой. Правильно для платёжных и auth-эндпоинтов.

**Правильный ответ на интервью:** решение зависит от эндпоинта; по умолчанию — fail-open с локальным «аварийным» лимитером (по памяти процесса, грубый, например 50 RPS на инстанс).

### 6.4 Синхронизация часов
Token bucket использует `now`. Расхождение часов инстансов на 5 сек → токены начисляются неправильно.
- NTP обязателен
- Или `TIME` из Redis внутри скрипта (точка истины одна)
- В GCRA расхождение часов ещё критичнее

## 7. Где ставить лимитер

| Место | Плюсы | Минусы |
|---|---|---|
| **Клиентская библиотека** | Нет сети | Не защищает от злого клиента |
| **API Gateway / Envoy** | Один компонент на всё, до бизнес-логики | Общий лимит по всем эндпоинтам |
| **Сервис-приложение** | Знает бизнес-контекст (лимит на «отправить письмо» vs «прочитать») | Дублирование кода, нагрузка на каждый сервис |
| **CDN/WAF (Cloudflare)** | Отсекает DDoS до вашей инфраструктуры | Грубые лимиты, нет контекста |

**Реальная практика — несколько уровней:**
1. CDN/WAF — грубый анти-DDoS (10k RPS на IP)
2. API Gateway — лимиты по API-ключу, общие
3. Сервис — бизнес-лимиты (например, 5 попыток ввода пароля/мин)

---

## 8. Итог

| Аспект | Решение | Почему |
|---|---|---|
| Алгоритм | Token Bucket | Контролируемый burst + строгая средняя скорость |
| Хранение | Redis + Lua-скрипт | Атомарность без гонок, 0.3 мс |
| Масштаб | Redis Cluster + локальный предфильтр | 1 млн RPS, защита от горячих ключей |
| При отказе | fail-open + аварийный локальный лимит | Простой лимитера хуже лишнего трафика |
| Клиенту | 429 + `Retry-After` + `X-RateLimit-*` | Корректный backoff на стороне клиента |
| Уровни | WAF → Gateway → Сервис | Разная гранулярность задач |

**Главная мысль для интервью:** главный вопрос не «какой алгоритм», а **где хранить состояние** (централизованно — точно, но +RTT; локально — быстро, но приблизительно) и **что делать при отказе** (fail-open или нет). Token bucket — стандартный ответ, но упоминание проблемы границы fixed window и стоимости sliding log показывает глубину.
