# 06. Базы данных: SQL и NoSQL, когда что выбирать

## Суть

Выбор базы данных — одно из первых архитектурных решений. SQL (реляционные) дают строгую схему, ACID-транзакции и мощные запросы (JOIN, агрегации). NoSQL жертвует частью этого ради горизонтальной масштабируемости, гибкой схемы или специфической модели данных. На собеседовании нужно уметь объяснить, **почему** для данной системы выбран тот или иной вариант, и какие компромиссы.

---

## SQL (реляционные БД)

**Представители:** PostgreSQL, MySQL, SQL Server, Oracle.

**Свойства:**
- **Строгая схема** — таблицы, колонки, типы. Изменение схемы — миграция.
- **ACID-транзакции** — атомарность, консистентность, изолированность, долговечность. Гарантия: платёж либо прошёл, либо нет, без промежуточных состояний.
- **SQL** — декларативный язык запросов. JOIN по нескольким таблицам, агрегации, подзапросы, оконные функции.
- **Внешние ключи** — целостность связей на уровне БД.
- **Индексы** — B-tree по умолчанию.

**Масштабирование:** преимущественно вертикально (больше CPU/RAM/SSD). Реплики — для чтения. Шардинing возможен, но сложен: JOIN между шардами, распределённые транзакции.

**Когда выбирать:**
- Сложные связи между сущностями (банковский счёт → переводы → клиенты → счета-фактуры).
- Нужна строгая консистентность (финансы, инвентаризация, бронирование).
- Данные хорошо укладываются в таблицы и редко меняют структуру.
- Ад-hoc запросы и аналитика по связанным данным (JOIN-heavy).

## NoSQL

Не один тип — а четыре разные модели. Общее: гибкая схема, горизонтальная масштабируемость, отказ от полноценного ACID (часто eventual consistency).

### 1. Документные (MongoDB, CouchDB, Firestore)

Данные — JSON-подобные документы, сгруппированные в коллекции. Один документ = одна запись со всеми связанными данными внутри.

```
{
  "_id": "order-42",
  "user": { "name": "Максим", "email": "max@example.com" },
  "items": [
    { "sku": "DK-01", "name": "Donut", "qty": 3, "price": 150 }
  ],
  "status": "paid",
  "total": 450
}
```

**Плюс:** читаем заказ одним запросом — не нужен JOIN. Гибкая схема: разные документы в одной коллекции могут иметь разные поля.
**Минус:** если нужно найти все заказы с товаром DK-01 — сканирование или денормализация. Нет JOIN.
**Когда:** контент-системы (CMS), каталоги товаров, профили пользователей, блоги. Документ самодостаточен, связи слабые.

### 2. Ключ-значение (Redis, Memcached, DynamoDB)

Просто `key → value`. Максимальная скорость, минимум логики в хранилище.

**Плюс:** O(1) чтение/запись, микросекунды. Горизонтальное масштабирование тривиально (хэш ключа → шард).
**Минус:** нет запросов по содержимому, нет secondary indexes (в базовом виде). Redis добавляет структуры данных (списки, множества, sorted sets).
**Когда:** кэш, сессии, счётчики, очереди, real-time лидерборды. Не основное хранилище бизнес-данных.

### 3. Колоночные / широкостолбные (Cassandra, HBase, ScyllaDB)

Данные хранятся по колонкам, а не по строкам. Строка может иметь миллионы колонок. Распределены по узлам через consistent hashing.

**Плюс:** запись очень быстрая (append-only, LSM-tree). Чтение по ключу строки — быстро. Линейное масштабирование — добавляй узлы. Нет single point of failure.
**Минус:** нет JOIN, запросы только по ключу строки и ключу колонки. Eventual consistency — последние записи могут быть не синхронизированы между репликами.
**Когда:** временные ряды (IoT, метрики, логи), лента событий, данные с очень высокой скоростью записи и доступом по ключу. Cassandra пишет миллионы записей в секунду на кластере.

### 4. Графовые (Neo4j, Dgraph, Amazon Neptune)

Узлы и рёбра — первые классы. Рёбра имеют типы и свойства.

**Плюс:** обход графа (друзья друзей, рекомендации, пути) за миллисекунды, тогда как в SQL это рекурсивные JOIN и экспоненциальный рост.
**Минус:** плохо масштабируется горизонтально (граф распределён — обходы跨 узлов дороги). Ограниченный набор запросов (Cypher, Gremlin).
**Когда:** социальные сети, фрод-детекция, рекомендации, анализ связей, knowledge graph.

## Как выбирать: ключевые вопросы

| Вопрос | SQL | NoSQL |
|--------|-----|-------|
| Структура данных стабильна? | Да → SQL | Меняется часто → документная |
| Нужны JOIN и сложные запросы? | Да → SQL | Нет → любая NoSQL |
| Строгая консистентность обязательна? | Да → SQL | Допустима eventual → колоночная/ключ-значение |
| Объём данных растёт быстрее железа? | Нет → SQL | Да → Cassandra/ DynamoDB |
| Доступ по сложным связям? | Да → SQL или графовая | Граф связей → Neo4j |
| Скорость записи — главный приоритет? | Среднее | Высокая → Cassandra/Redis |

## Практический подход: полиглот-персиcтентность

Реальные системы редко живут на одной БД. Один сервис — одно хранилище:

- **PostgreSQL** — пользователи, заказы, платежи (ACID, JOIN, миграции).
- **Redis** — кэш, сессии, rate limiter.
- **Cassandra** — логи событий, метрика, лента активности (массовая запись, доступ по ключу).
- **Elasticsearch** — поиск (полнотекстовый, не из этого списка, но часто в паре с SQL).

Ключевой принцип: основной стore данных — SQL для транзакционных данных; NoSQL — для специфичных нагрузок рядом.

## Примеры

### E-commerce (Amazon)
- **PostgreSQL** — заказы, платежи, инвентарь (ACID: нельзя списать товар дважды).
- **Elasticsearch** — поиск по каталогу миллионов товаров.
- **Redis** — корзина пользователя, кэш карточек товаров.
- **Cassandra** — история просмотров, clickstream.

### Instagram
- **PostgreSQL / Cassandra** — пользовательские данные, лента.
- **Redis** — feed, лайки, счётчики.
- Шардинг PostgreSQL по user_id — каждый шард держит подмножество пользователей.

### IoT-платформа
- Устройства шлют по 10 значений/сек. 1 млн устройств = 10 млн записей/сек.
- **Cassandra** — линейное масштабирование записи, TTL на старые данные, доступ по device_id + timestamp.
- SQL не справится с такой скоростью записи без агрессивного шардирования.

## Ловушки

1. **«NoSQL = нет схемы»** — миф. Схема просто переезжает из БД в код. Если документ эволюционирует, нужно версионирование и миграции на уровне приложения.
2. **«NoSQL быстрее SQL»** — зависит от нагрузки. PostgreSQL на 10k QPS чтения с индексом отрабатывает за миллисекунды. NoSQL выигрывает на масштабе и специфичной модели, а не всегда.
3. **«ACID только в SQL»** — нет. MongoDB поддерживает multi-document ACID с 4.0. Redis — atomic на уровне команды. Разница в scope и defaults, не в принципе.
4. **«JOIN можно заменить денормализацией»** — да, ценой избыточности и сложности обновления. Поменял цену товара — обнови во всех заказах, где он есть. Или не обновляй (историческая цена в момент заказа).

## Вопросы для обсуждения

1. **Выбор для конкретной системы.** Ты проектируешь Pinterest — пользователи сохраняют «пины» (картинки) на «доски», лента рекомендаций, миллионы пинов в секунду на чтение. Какую БД выбрать для: (a) профили пользователей и доски; (b) лента рекомендаций; (c) счётчики лайков/сохранений? Почему?

2. **Миграция SQL → NoSQL.** Стартап начал на PostgreSQL, вырос до 50 млн пользователей. Главный сервис — лента действий (как в FB: «Вася лайкнул фото, Петя добавил пина»). Запись 200k событий/сек. Можно ли остаться на PostgreSQL? Что надо сделать, и когда NoSQL оправдан?

3. **Денормализация.** В SQL у тебя `orders` и `order_items` (связь 1:N). Переносишь в MongoDB: как выглядит документ заказа? Что происходит со «старым» запросом «дай все заказы с товаром X»? Как решить без JOIN?

4. **ACID scope.** Перевод денег со счёта A на счёт B: списание + зачисление. В SQL — одна транзакция, откат при сбое. В Cassandra нет распределённых транзакций между разными ключами строк. Как гарантировать, что деньги не пропадут?

5. **Расчёт.** Система хранит лог кликов: 10 млн пользователей × 100 кликов/день × 200 байт/клик. (a) Сколько данных в день и в год? (b) Какая БД лучше — PostgreSQL или Cassandra — и почему? (c) Если хранить только последние 90 дней, что меняется?
