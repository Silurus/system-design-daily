# 05. CDN и кэш на краю

**Дата:** 2026-11-13

---

## Суть

CDN (Content Delivery Network) — сеть географически распределённых серверов (PoP — Points of Presence), которые кэшируют контент ближе к пользователю. Вместо запроса в Амстердам из Токио — запрос до ближайшего PoP в Осаке.

Ключевой эффект: снижение **latency** за счёт физического расстояния + разгрузка origin-сервера.

Пример: страница загружается за 200 мс с CDN против 800 мс с origin в другом континенте. При 100 млн DAU и 50 ресурсов на страницу — без CDN origin умирает.

---

## Как работает

### Маршрутизация (DNS-based)

1. Пользователь запрашивает `cdn.example.com/image.jpg`
2. DNS возвращает IP ближайшего PoP (геолокация или Anycast)
3. PoP проверяет кэш: **hit** → отдаёт; **miss** → запрос к origin, кэшируем, отдаём

### Pull CDN (наиболее распространён)

CDN сам подтягивает контент с origin при первом cache miss. Прозрачно для origin.

- Плюсы: не нужно заливать файлы вручную, кэш заполняется только востребованным.
- Минусы: первый запрос идёт к origin (cold miss); если origin недоступен — PoP вернёт ошибку.

### Push CDN

Вы загружаете файлы на CDN заранее (через API). CDN хранит их везде.

- Плюсы: нет cold miss; работает когда origin недоступен.
- Минусы: нужно явно управлять инвалидацией; неэффективно для длинного хвоста (long tail) — большинство файлов запросят редко, а место занято.

**Когда что:** Pull — для медиа, изображений, JS/CSS (большой Long Tail). Push — для критичных файлов малого объёма (логотипы, шрифты, видео-трейлеры топ-N).

---

## Что кэшировать

| Кэшируется охотно | Не кэшируется / осторожно |
|---|---|
| Статика: JS, CSS, изображения | Персонализированные данные (профиль) |
| Видео (HLS-сегменты по 2–10 сек) | Платёжные страницы |
| Публичные API-ответы | Данные с авторизацией (Authorization-header) |
| HTML для анонимных пользователей | Real-time цены/остатки |

Правило: если ответ одинаков для всех запросов с одинаковым URL — его можно кэшировать.

## Cache-Control и TTL

Браузер и CDN читают заголовки HTTP:

```
Cache-Control: public, max-age=86400, s-maxage=3600
```

- `max-age` — TTL для браузерного кэша.
- `s-maxage` — TTL для shared кэшей (CDN). Переопределяет `max-age` для них.
- `public` — разрешает кэшировать CDN (важно: без `public` ответ с `Authorization` не кэшируется).
- `no-store` — вообще не кэшировать.
- `stale-while-revalidate` — отдай старое, обнови фоном.

Стратегия версионирования: `main.a3f7c9.js` — хэш в имени файла, TTL = 1 год. При изменении — новый хэш, новый URL → старый кэш не нужно инвалидировать вообще.

## Инвалидация CDN

Проблема: файл изменился на origin, но PoP хранит старую версию до истечения TTL.

Решения:
1. **Versioned URL** (`v2/image.jpg`) — самое надёжное, старый URL сам протухнет.
2. **API purge** — явный вызов CDN API (Cloudflare, Fastly). Мгновенно, но дорого на масштабе (тысячи PoP).
3. **Surrogate keys / cache tags** — помечаем группу ресурсов тегом (например, `product-42`). При изменении продукта — одним вызовом чистим все связанные ресурсы. Поддерживают Fastly, Varnish.

## Edge Computing

CDN PoP — не просто кэш. Современные платформы (Cloudflare Workers, Fastly Compute, AWS Lambda@Edge) позволяют запускать код на PoP.

Примеры:
- **A/B-тестирование** на краю: решение о варианте без запроса к origin.
- **Аутентификация JWT** на PoP: не тратим round-trip к auth-сервису.
- **Image resizing** на лету: один origin-файл → разные размеры для разных устройств.
- **Geo-блокировка** по IP без нагрузки на backend.

Ограничения: ограниченная память, нет прямого доступа к БД, сложнее отлаживать.

## Пример: YouTube видео

HLS-видео разбивается на сегменты по 2–6 сек (`seg_001.ts`, `seg_002.ts`). Каждый сегмент — статичный файл, TTL = 24 ч на CDN.

- 1 млн одновременных зрителей, каждый тянет 1 сегмент/5 сек = **200 000 RPS на origin**
- С CDN hit rate 95% → origin получает **10 000 RPS**

Thumbnail и первые N сегментов — push CDN (всегда прогреты). Остальное — pull.

## Вопросы для обсуждения

1. **Pull vs Push.** Новостной сайт: 10 000 статей, 500 из них получают 95% трафика. CDN стоит по хранилищу. Какую стратегию выбрать и почему? Что будет с первым читателем «вирусной» статьи?

2. **Cache-Control.** API `/api/product/42` возвращает цену товара. Цена меняется раз в час, аудитория — 500 000 уникальных пользователей/час. Какой `Cache-Control` выставить? Как избежать ситуации, когда пользователь видит устаревшую цену?

3. **Инвалидация.** Интернет-магазин. Карточка товара в HTML кэширована на CDN (TTL 24 ч). Менеджер поменял цену в admin-панели. Пользователи в Европе видят старую цену ещё 23 часа. Какие два механизма помогут? Какие у них компромиссы?

4. **Edge code.** Мобильное приложение получает JSON `/api/feed`. Вы хотите A/B-тест: 50% пользователей видят `version=2` ленты. Как реализовать на уровне CDN без изменения backend? Что нужно учесть?

5. **Расчёт.** Сервис хранит аватары: 50 млн пользователей, каждый открывает 20 профилей в день. Аватар — 50 КБ. Посчитай: (a) трафик к origin без CDN; (b) трафик к origin при CDN hit rate 90%; (c) сколько нужно origin-пропускной способности в обоих случаях?
