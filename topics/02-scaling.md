# 02. Масштабирование

**Дата:** 2026-11-10  
**Статус:** пройдена

## Суть

Когда один сервер не справляется — два пути: **вертикальное** (добавить CPU/RAM/SSD) и **горизонтальное** (добавить серверы). Вертикальное проще до первого потолка, горизонтальное сложнее (нужен балансировщик, stateless), но даёт неограниченный рост.

Ключ горизонтального масштабирования — **stateless-сервисы**: процесс не хранит состояние между запросами, любой инстанс обрабатывает запрос идентично. Состояние выносят в распределённое хранилище (Redis, БД).

## Как работает

### Вертикальное масштабирование

- Один инстанс, растут ресурсы (16 → 32 → 64 CPU, 128 → 256 ГБ RAM)
- **Потолок железа:** ~100 CPU, 1–2 ТБ RAM (AWS i4i.32xlarge)
- Требует downtime при апгрейде (кроме hot-swap RAM на enterprise)
- **Стоимость нелинейная:** i4i.32xlarge дороже 4×i4i.8xlarge

### Горизонтальное масштабирование

- N инстансов за балансировщиком, каждый обрабатывает ~1/N трафика
- **Stateless:** сессия в Redis/memcached, файлы в S3, БД отдельно
- Deployment: rolling update без downtime
- **Стоимость линейная:** 10×инстанс = 10× цена одного

### Stateless vs. stateful

**Stateless:**
- Запрос независим, можно убить инстанс без потери данных
- Пример: REST API, который читает из БД

**Stateful:**
- Хранит состояние (WebSocket-соединения, in-memory cache)
- Решения:
  - **Sticky sessions** (балансировщик привязывает клиента к инстансу)
  - **Вынос state в Redis/БД** (pub/sub для WebSocket)
  - **Вертикальное**, если координация дороже (in-memory graph)

## Trade-offs

| | Вертикальное | Горизонтальное |
|---|---|---|
| **Плюс** | Проще: нет синхронизации, один инстанс | Линейный рост, отказоустойчивость, zero-downtime |
| **Минус** | Потолок железа, SPOF, downtime при апгрейде | Сложнее: балансировщик, stateless, координация |
| **Стоимость** | Нелинейная (мощное железо дороже) | Линейная |
| **Когда** | Старт, до 5–10k QPS, stateful-нагрузка | Масштаб, отказоустойчивость, rolling updates |

## Схема: Эволюция архитектуры

```
Этап 1: Монолит (вертикальное)
┌─────────────────┐
│  App + DB       │
│  16 CPU, 32 GB  │
└─────────────────┘

Этап 2: App отдельно (вертикальное)
┌─────────────┐      ┌──────────────┐
│  App        │─────▶│  PostgreSQL  │
│  32 CPU     │      │  64 GB RAM   │
└─────────────┘      └──────────────┘

Этап 3: Горизонтальное
       ┌──────────────┐
       │ Load Balancer│
       └──────┬───────┘
         ┌────┴────┬────────┐
    ┌────▼───┐ ┌──▼────┐ ┌─▼─────┐
    │ App #1 │ │App #2 │ │App #3 │  (stateless)
    └────┬───┘ └──┬────┘ └─┬─────┘
         └────────┼────────┘
              ┌───▼────────┐
              │ PostgreSQL │  (master + replicas)
              │ + Redis    │
              └────────────┘
```

## Примеры

### Netflix

- Тысячи микросервисов (рекомендации, кодирование, профили) — stateless
- Kubernetes автоматически масштабирует: CPU > 70% → новые поды, CPU < 30% → удаляет
- Статические данные (профили) и кэш (Redis) реплицируются отдельно
- Один сервис обработки видео — 100 подов, каждый кодирует кусок, никакого состояния между ними

### Instagram

- Stateless Django за nginx → тысячи инстансов
- PostgreSQL (вертикальное до потолка) + Cassandra (горизонтальное шардирование по user_id)
- Uploaded files → S3 (горизонтальное хранилище)

### Slack (WebSocket — stateful, но горизонтальное)

- Тысячи WebSocket-серверов, sticky sessions (балансировщик привязывает клиента к инстансу)
- Redis pub/sub для маршрутизации сообщений между инстансами
- При падении инстанса клиент переподключается, восстанавливает state из Redis

## Сигналы перехода на горизонтальное

1. **Упёрлись в потолок железа** (~100 CPU, 1–2 ТБ RAM)
2. **Стоимость вертикального > горизонтального** (i4i.32xlarge дороже 4×i4i.8xlarge)
3. **Нужен rolling update без downtime** (99.9% SLA не позволяет останавливать монолит)
4. **Стоимость downtime** (апгрейд требует остановки, но у вас high availability)

## Решение проблем

### Uploaded files в `/tmp` инстанса

**Проблема:** следующий запрос попадёт на другой инстанс → 404; rolling update убьёт инстанс → файл потерян навсегда.

**Решение:** S3/object storage. Upload идёт через signed URL напрямую в S3, или через бэкенд → immediate write в S3.

### WebSocket с in-memory state

**Проблема:** нельзя убить инстанс без потери соединений.

**Решение:**
- Sticky sessions + graceful shutdown (30 сек на переподключение клиентов)
- Redis pub/sub для маршрутизации между инстансами
- State в БД/Redis (online status, typing indicators)

## Ключевые выводы

1. **Вертикальное — до первого потолка** (проще, дешевле, но SPOF и downtime).
2. **Горизонтальное требует stateless** — сессии в Redis, файлы в S3, БД отдельно.
3. **Stateful можно масштабировать горизонтально** через pub/sub, sticky sessions, или вынос state в распределённое хранилище.
4. **Сигнал перехода:** упёрлись в железо, стоимость вертикального выше, нужен zero-downtime deploy.
